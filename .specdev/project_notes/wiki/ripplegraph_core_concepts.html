Ripplegraph Core Concepts

A practical wiki-style introduction for people who have never seen Ripplegraph before.

Ripplegraph is a small runtime for building reliable agent-driven workflows. It does not replace an LLM or a CLI. It gives them rails: graph position, validation, checkpoints, transitions, gates, and durable audit logs.

Shortest definition: Ripplegraph is the workflow backbone. The graph owns flow; the host agent owns the work.

The Problem It Solves

Without rails

Agents drift

Long-running CLI workflows can lose track of where they are, what has already been approved, and what should happen next.

Without contracts

Steps become vague

Prompts, validators, business commands, and output shapes can get mixed into ad hoc code or chat history.

Without state

Recovery is hard

If context is lost, the host needs a trustworthy source of current position, recent outputs, and allowed next actions.

Core Mental Model

Graph Package

Declares workflow structure, nodes, schemas, effects, gates, and host-facing metadata.

→
Ripplegraph Runtime

Tracks position, validates outputs, writes checkpoints, and records transitions.

→
Host CLI / Agent

Renders prompts, runs tools, calls validators, talks to users, and submits results back.

Who Owns What?

Ripplegraph Owns

  • Current graph position
  • Checkpoint files
  • Transition logs
  • Node output validation
  • Gate decisions
  • Effect preflight checks
  • Workflow composition through workflowRef
  • Side-channel and reconciliation audit records

Host CLI / Agent Owns

  • LLM calls and prompt execution
  • Rendering user interactions
  • Running shell commands or tools
  • Calling validators
  • Reading backend systems
  • Business logic and adapters
  • Domain-specific files and formats
  • Deciding what to do when drift is detected

The Main Building Blocks

Concept Plain-English Meaning Why It Matters
graph package A folder containing a workflow definition and metadata. Lets workflows be reusable, registered, versioned, and tested independently.
node A unit of work in the workflow. Each node has a purpose, optional instructions, output schema, and edges to next nodes.
edge A transition from one node to another. Keeps flow deterministic instead of leaving routing to chat memory.
gate An external decision point. Used for human approvals, review tools, or other decisions that should be explicit.
checkpoint The saved runtime state for a run. Allows recovery after context loss, process restart, or user interruption.
transition log An append-only audit log of runtime events. Shows what happened: start, step, decide, suspend, resume, side-channel, reconcile.
workflowRef A node that enters another workflow package. Lets larger systems be built from smaller subgraphs.
callable An isolated graph-shaped function. Useful for reusable typed work that should not mutate the focused workflow run.

Workspace Front Door: Registry And Dispatcher

A Ripplegraph workspace can contain many graph packages. The workspace needs a way to know what is available, and the host needs a way to route a user request to the right action. These are separate concepts: the registry is the catalog, and the dispatcher is the front door.

Catalog

Registry

The registry lives at .ripplegraph/registry.json. It records registered graph packages in the workspace.

  • Graph id
  • Version
  • Kind: dispatcher, workflow, or callable
  • Package path
  • Title, description, activation hints, and effects
Router

Dispatcher Graph

A dispatcher is a graph package with "kind": "dispatcher". It helps route user intent to a structured action.

  • Start a workflow run
  • Resume or switch runs
  • List runs
  • Ask the user a question
  • Call a callable graph

Dispatcher Is Not A Master Workflow

It is tempting to call the dispatcher a “master workflow,” but that is not quite right. A dispatcher does not own the durable workflow position for every run. It helps the host decide what structured action to take.

Graph Kind Plain Meaning Runtime Behavior
dispatcher Workspace front desk Routes user intent to actions like start_run, resume_run, list_runs, ask_user, or call_graph.
workflow Durable user-visible run Has checkpoints, position, gates, outputs, transition logs, suspend/resume, and completion.
callable Graph-shaped function Runs in isolated call state under .ripplegraph/calls/ and does not mutate the focused workflow run.
A root workflow with many workflowRef child graphs is different from a dispatcher. The root workflow owns one durable run. The dispatcher helps choose which run/action should happen.

A Run From Start To Finish

The important detail is that Ripplegraph does not guess the next step. It validates submitted data, picks the next edge, updates the checkpoint, and appends a transition log entry.

Host-Facing Metadata

Graph packages can declare metadata that tells the host what it should render or resolve. Ripplegraph validates and exposes the metadata, but the host performs the actual action.

Interaction Metadata

interaction can describe choices, free text, confirmation, or forms. A host CLI can render these consistently.

User-Turn Interrupts

interrupt means the workflow needs a real user turn before automatic continuation should proceed.

Tool Contracts

toolContract declares a host command, schemas, effects, and an optional validator. Ripplegraph does not execute it.

Validators

validators names host-owned checks that a consumer CLI can resolve and run outside the runtime.

Side-Channel And Reconciliation Records

Some useful host actions should not advance the graph. Loading backend state, refreshing an artifact, or checking an external FSM should be audited, but the workflow cursor should stay put.

Operation What It Records Position Behavior
side_channel A host says it performed a side-channel action and submits input/output metadata. Does not move. from and to are the same position.
reconcile A host submits an external snapshot and optional expected snapshot. Ripplegraph reports alignment or drift. Does not move. The host decides what to do if drift is found.

How To Build On Ripplegraph Incrementally

1. One Workflow

Start with a simple graph package and run it end to end.

→
2. One Gate

Add a decision point and test the host rendering/submission path.

→
3. One Subgraph

Introduce workflowRef and test parent-child behavior.

Rule of thumb: keep business flow in graph packages, keep business execution in the host, and keep runtime truth in Ripplegraph.

A Story: Building The Support Triage CLI

Imagine a team is building a CLI called SupportPilot. SupportPilot helps an agent triage customer tickets, inspect workspace files, ask for approval, and produce a final response plan. The team wants the workflow to be reliable, recoverable, and testable. They put the flow in Ripplegraph and keep business execution in their CLI.

Cast Of Real Names

Name Type Role In The Story
supportpilot Host CLI Renders prompts, calls tools, reads ticket data, runs validators, and submits results to Ripplegraph.
support-triage Workflow graph package The main user-visible workflow.
ticket-context Child workflow graph package A reusable subgraph entered through workflowRef.
summarize-ticket Callable graph package An isolated graph-shaped function for producing a typed summary.
ticket-output-validator Host validator A validation routine owned by SupportPilot, not by Ripplegraph.
refresh-ticket-state Side-channel action A host action that refreshes backend state without advancing the workflow.

Step 1: The Team Creates A Graph Package

The first package is support-triage. It has a few nodes:

  • classify-ticket: the host agent reads the ticket and submits a category.
  • load-context: a workflowRef node that enters the child graph ticket-context.
  • review-plan: a gated approval node where a user must approve or reject the response plan.
  • finalize: the terminal node.

This package owns the flow. SupportPilot does not hard-code the order of these steps. Ripplegraph reads the package, validates it, and starts a run.

Before That: The Workspace Registers Its Packages

SupportPilot registers three graph packages into the workspace registry: 

ripplegraph graph register .ripplegraph/graphs/workspace-dispatcher --workflow-root .
ripplegraph graph register .ripplegraph/graphs/support-triage --workflow-root .
ripplegraph graph register .ripplegraph/graphs/summarize-ticket --workflow-root .

The registry file .ripplegraph/registry.json now acts as the workspace catalog. When the user says “triage ticket TCK-1007,” SupportPilot can ask the dispatcher graph what action to take. 

ripplegraph dispatch --request "triage ticket TCK-1007" --workflow-root .

The host agent reads the dispatcher context and submits a structured action: 

ripplegraph dispatch --action '{"action":"start_run","graphId":"support-triage","runId":"triage-TCK-1007"}' --workflow-root .

This is the front-door pattern: the dispatcher routes intent, while the support-triage workflow owns the durable run.

Step 2: SupportPilot Starts A Run

A support engineer types:

supportpilot start support-triage --ticket TCK-1007

Under the hood, SupportPilot calls Ripplegraph. Ripplegraph creates a run, writes a checkpoint, and returns the current state: 

{
  "status": "ok",
  "run": { "id": "triage-TCK-1007", "status": "active" },
  "position": { "graph": "support-triage", "node": "classify-ticket" },
  "node": {
    "id": "classify-ticket",
    "purpose": "Classify the customer ticket",
    "outputSchema": {
      "type": "object",
      "required": ["category"],
      "properties": {
        "category": { "enum": ["bug", "question", "feature"] }
      }
    }
  },
  "responseContract": { "command": "step", "acceptedFormats": ["json"] }
}

This tells SupportPilot: “You are at classify-ticket. Do the work, then submit JSON matching the schema.”

Step 3: The Host Does Work, Ripplegraph Validates

SupportPilot reads the ticket from its own ticket adapter. Ripplegraph does not read the ticket system. The host agent decides the ticket is a bug and submits:

ripplegraph step --output '{"category":"bug"}'

Ripplegraph validates the output against classify-ticket.outputSchema, stores the node output, appends a step transition, and moves to the next node.

The LLM can produce content, but the graph controls the route. The host does not freely choose the next node.

Step 4: The Workflow Enters A Subgraph

The next node is load-context. It is not a normal work node. It has: 

{
  "workflowRef": {
    "graphId": "ticket-context",
    "inputMap": { "ticketId": "$.ticket.id" },
    "outputMap": { "context": "$.summary" }
  }
}

Ripplegraph enters the child workflow ticket-context and pushes a frame onto the run stack. This means the main run is still one run, but it is temporarily executing a child graph.

The child graph might gather repository context, inspect related tickets, or call a host validator. When the child completes, Ripplegraph returns to the parent workflow and continues from the next parent node.

Step 5: Host-Facing Metadata Tells The CLI What To Show

Now the run reaches review-plan. This node has a gate and host-facing metadata: 

{
  "gate": {
    "type": "external_decision",
    "interaction": {
      "id": "plan-approval",
      "kind": "choice",
      "prompt": "Approve the support response plan?",
      "choices": [
        { "label": "Approve", "value": "approved" },
        { "label": "Revise", "value": "revise" }
      ]
    },
    "decisionSchema": {
      "type": "object",
      "required": ["decision"]
    }
  },
  "interrupt": {
    "requiresUserTurn": true,
    "reason": "A human must approve the customer-facing response."
  }
}

Ripplegraph exposes this metadata in state. SupportPilot sees node.gate.interaction and renders a choice prompt. It also sees interrupt.requiresUserTurn, so it stops automatic tool execution and asks the support engineer.

Step 6: A Side-Channel Action Refreshes Backend State

Before approving, the engineer clicks “Refresh ticket state.” The graph package declared: 

{
  "sideChannelActions": [
    {
      "id": "refresh-ticket-state",
      "purpose": "Refresh the current ticket state without advancing the workflow.",
      "effects": ["read_ticket_backend"]
    }
  ]
}

SupportPilot performs the backend read. Then it records the fact in Ripplegraph:

ripplegraph side-channel --action refresh-ticket-state --output '{"status":"open"}'

Ripplegraph appends a side_channel transition log entry. The current graph position remains support-triage/review-plan.

Side-channel actions are useful because they are auditable, but they do not move the workflow cursor.

Step 7: Reconciliation Detects Drift

SupportPilot expects the backend ticket to still be open, but the backend now says closed. It submits a reconciliation record:

ripplegraph reconcile --source ticket-backend --snapshot '{"status":"closed"}' --expected '{"status":"open"}'

Ripplegraph compares the two JSON snapshots and returns: 

{
  "status": "ok",
  "position": { "graph": "support-triage", "node": "review-plan" },
  "reconciliation": {
    "source": "ticket-backend",
    "aligned": false
  }
}

Ripplegraph does not decide what to do about the drift. SupportPilot owns that policy. It might warn the user, refresh the plan, or ask for a new decision.

Step 8: The User Makes The Gate Decision

After reviewing the refreshed state, the engineer chooses “Approve.” SupportPilot submits:

ripplegraph decide --decision '{"decision":"approved"}'

Ripplegraph validates the decision, stores it in gateDecisions, appends a decide transition, and moves to finalize.

Step 9: A Callable Handles Reusable Typed Work

Separately, SupportPilot has a callable graph package named summarize-ticket. It is not a user-turn workflow. It behaves like a typed graph-shaped function:

ripplegraph call --graph summarize-ticket --input '{"ticketId":"TCK-1007"}'

The callable stores its own checkpoint under .ripplegraph/calls/. It does not mutate the focused workflow run. Ripplegraph deliberately rejects gates and host-interaction metadata in callables so they stay isolated and function-like.

What Ripplegraph Is Not

Not an LLM framework

It does not call OpenAI, Claude, or local models. The host agent does that.

Not a shell runner

It does not execute arbitrary commands. It declares and audits contracts around host-owned commands.

Not a domain parser

It does not parse Oceanlive, SpecDev, TOML, CSV, or business-specific files. Host packages own that.

Not the product UI

It returns state and contracts. Consumer CLIs decide how to render them for humans.
